proxy_pass URI Surgery

Each drill row comes down to one decision path. Find the branch first, then do the string surgery: cut what the location matched, paste what proxy_pass says, and keep the rest exactly as it was. Nginx copies characters. It doesn't know about path segments and doesn't tidy slashes.

/cut removed from the request /v2/ added by proxy_pass users carried over unchanged v1/items regex capture ?page=2 dropped

The drill, row by row

a
location /a/ { proxy_pass http://127.0.0.1:8001; }

With no URI in proxy_pass, nginx doesn't touch the URI at all. The location only decides where the request goes, not what it looks like.

b
location /b/ { proxy_pass http://127.0.0.1:8001/; }
regex? no→variable? no→URI after host? yes: /
Prefix replace
Request/b/v1/stats Cut /b/, paste //v1/stats Backend gets/v1/stats

Clean strip. The location ends in / and the URI is /, so exactly one slash goes out and one comes back.

c
location /c { proxy_pass http://127.0.0.1:8001/; }
regex? no→variable? no→URI after host? yes: /
Prefix replace
Request/c/v1/stats Cut /c, paste ///v1/stats Backend gets//v1/stats

Double slash. The location is /c with no trailing slash, so the cut stops before the next /. That slash stays on the remainder, and proxy_pass adds its own.

Fix: make both sides end in a slash, location /c/ with proxy_pass …/; (same as row b).

c2
location /c { proxy_pass http://127.0.0.1:8001/; }
regex? no→variable? no→URI after host? yes: /
Prefix replace
Request/catalog Cut /c, paste //atalog Backend gets/atalog

Wrong location matched. /catalog starts with the characters /c, so location /c matches it. A prefix location compares characters, not path segments. This is the same trap as Sprint 1 Day 2.

Fix: location /c/ no longer matches /catalog at all.

d
location /d/ { proxy_pass http://127.0.0.1:8001/v2; }
regex? no→variable? no→URI after host? yes: /v2
Prefix replace
Request/d/users Cut /d/, paste /v2/v2users Backend gets/v2users

Slashes glued. This is the mirror image of row c. The trailing slash of /d/ was part of the cut, and /v2 doesn't put one back.

Fix: proxy_pass http://127.0.0.1:8001/v2/; (row e).

e
location /e/ { proxy_pass http://127.0.0.1:8001/v2/; }
regex? no→variable? no→URI after host? yes: /v2/
Prefix replace
Request/e/users Cut /e/, paste /v2//v2/users Backend gets/v2/users

Clean replace. Both sides end in /. The rule of thumb: if the location ends in a slash, the proxy_pass URI should too.

f
location ~ ^/f/(.*)$ { proxy_pass http://127.0.0.1:8001/$1; }
regex? yes→stop here
Build from captures
Request/f/v1/items?page=2 Regex sees path only/f/v1/items $1 = v1/items Build / + $1/v1/items?page=2 Backend gets/v1/items

Query string lost. A regex has no fixed prefix, so there is nothing to cut. Whatever you write after the host is the full URI. The regex only runs against the path, so $1 never contains ?page=2, and nothing adds it back.

Fix: proxy_pass http://127.0.0.1:8001/$1$is_args$args;

g
location /g/ { set $be 127.0.0.1:8001; proxy_pass http://$be/; }
regex? no→variable? yes, with URI /→stop here
Variable + URI: full replace
Request/g/v1/stats Replace all with // Backend gets/

Everything goes to /. Once proxy_pass has a variable, nginx turns prefix replacement off. The URI you wrote replaces the entire request URI, for every request. It looks like row b but behaves completely differently.

Fix: drop the URI from proxy_pass and strip the prefix with rewrite instead (row h).

h
location /h/ { set $be 127.0.0.1:8001; rewrite ^/h/(.*)$ /$1 break; proxy_pass http://$be; }
regex? no→variable? yes, no URI→stop here
Rewrite first, then pass as-is
Request/h/v1/items?page=2 Step 1: rewrite/v1/items?page=2 Step 2: proxy_passno URI, so nothing cut or pasted Backend gets/v1/items?page=2

The correct way to strip a prefix with a variable backend. rewrite does the surgery, and it keeps the original query string by default. break stops further rewrite processing but stays in this location. Then proxy_pass has no URI, so it sends the rewritten URI exactly as it is.
