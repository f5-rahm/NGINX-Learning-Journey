## Findings From Building the Sprint

### TLS (Day 1)
* **Two gates in front of TLS 1.0/1.1.** The 1.31.6 default `ssl_protocols` excludes them (alert 70), and Ubuntu's OpenSSL `SECLEVEL=2` refuses them too. TLS 1.1 only worked with *both* `ssl_protocols TLSv1 TLSv1.1 ...` and `ssl_ciphers DEFAULT@SECLEVEL=0`. Even the client needs `-cipher DEFAULT@SECLEVEL=0`, or it fails locally with `no protocols available`.
* **The default `ssl_ciphers` (`HIGH:!aNULL:!MD5`) still allows CBC in TLS 1.2.** `ssl_ciphers` never touches TLS 1.3: with `ssl_ciphers` restricted, `TLS_AES_128_GCM_SHA256` still negotiated until `ssl_conf_command Ciphersuites` was set.
* **Dual certificates:** a modern client gets ECDSA. RSA-only sigalgs (TLS 1.3) or an `ECDHE-RSA` suite (TLS 1.2) get RSA. With only an ECDSA certificate, both RSA-only clients got alert 40, logged at `info` only (`no suitable signature algorithm`, `no shared cipher`).
* **SNI:** connecting by IP sends no SNI, so a `ssl_reject_handshake` default server refuses it (alert 112).
* **Resumption matrix** (2 workers, `s_client -sess_out/-sess_in`):

  | Config | Resumes | After reload |
  | :--- | :--- | :--- |
  | Defaults (tickets on, cache `none`) | Yes | No |
  | `ssl_session_tickets off`, no cache | No | No |
  | `shared` cache (tickets on or off) | Yes | Yes |
  | `builtin` cache, tickets off | Mostly (the first reconnect missed: per worker) | No |

* **Placement matters:** a shared cache only inside `server lumina.local`, behind a separate `ssl_reject_handshake` default server, did **not** survive reloads. Moving it to `http` level (or into the default server too) fixed it. Resumption happens in the default server's context.
* **TLS 1.3 tickets arrive after the handshake.** `echo | openssl s_client -sess_out` closes too early and saves nothing. The helpers keep the connection open with `(sleep 0.3) |`.
* **`s_client` prints `Verify return code: 0 (ok)` even when the handshake failed.** Don't grep for it to detect success; check for a cipher other than `(NONE)`.
* **`s_client`'s `New, TLSv1.0, Cipher is ...` line shows the cipher's spec version, not the negotiated protocol.** The `Protocol :` line in the session block is the real one.

### HTTP/2 and HTTP/3 (Day 2)
* Three parallel 2 s requests: one connection with `reqs=1,2,3` over HTTP/2, three connections over HTTP/1.1 (both ~2 s), and ~6 s with one HTTP/1.1 connection.
* **HPACK is visible in `$request_length`:** a 600-byte header cost 422 bytes, then 11 bytes on the repeat (HTTP/2). HTTP/1.1 paid 695 both times.
* **The upstream protocol is independent:** mocks saw HTTP/1.1 for h1, h2 and h3 clients. `proxy_http_version 2` exists on 1.31.6 and worked against an h2c NGINX backend.
* **HTTP/3 client:** the host's curl 7.81, `curlimages/curl:8.16.0` and Alpine 3.22's curl all lack HTTP/3. `alpine/curl-http3:8.11.0` (quiche) works.
* **QUIC SNI gap:** a TCP-only `ssl_reject_handshake` default server leaves UDP unprotected. An unknown SNI got a 200 over HTTP/3. Fix: `listen 8443 quic reuseport default_server;` on the catch-all, plain `listen 8443 quic;` on lumina. Two `reuseport`s on one port: `[emerg] duplicate listen options`.
* The `quic fixed bit is not set` lines at `info` level come from the quiche client and are harmless.

### Headers (Day 3)
* `add_header_inherit merge` exists on 1.31.6 and restores inherited headers in a child that adds its own.
* Without `always`, proxied 404/502 responses had none of the security headers. `always` covers them, over HTTP/3 too.

### Side Quest A (NGINX Plus R37.1)
* `ssl_certificate data:$var` from `keyval`: an empty store means alert 80 and `cannot load certificate "data:"`.
* **The API updates one key per PATCH** (`only one key can be updated`, 400). Cert and key under separate keys gave a window of failed handshakes (`SSL_use_PrivateKey` error). One key holding key + cert as one PEM bundle, used by both directives, rotated under a 40-handshake loop with 0 failures and unchanged worker PIDs.

* `$HOME` was empty in a non-login shell again. `--mount` refused to start (`bind source path does not exist: /plus/license.jwt`) instead of creating a directory, which is exactly why the convention uses `--mount`.

### Side Quest B (`nginx-module-acme` 0.4.1 + Pebble 2.8.0)
* `nginx-module-acme` installs from the nginx.org apt repo as a dynamic module (`load_module`).
* **A relative `state_path` resolves under `/var/cache/nginx`,** not the `-p` prefix: `mkdir() "/var/cache/nginx/state/pebble" failed`. Use an absolute path.
* The module creates `state_path` itself (`nginx:root`, mode 700). The `.crt`/`.key` inside are mode 666, so the directory is the only protection. A first test under `/root` failed to persist (`writing certificate to state directory failed`) only because `/root` isn't traversable by the `nginx` user.
* **HTTP-01 succeeded on a server whose only directive was `return 301`.** The module answers challenges before the rewrite phase. Pebble made 3 validation requests (multi-perspective).
* Pebble issued a **6-day** certificate with an empty subject (SAN only), and the module logged the CA's ARI renewal window.
* A restart reused the stored certificate (same serial). Before the first issuance, handshakes fail with alert 80.
* Pebble's image is distroless (no `cat`): copy `pebble.minica.pem` out with `docker create` + `docker cp`.

## Day 1
* **Q: Can Ubuntu be made to allow TLS 1.0/1.1? Does NGINX have its own crypto?** Verified on 8088:
  * NGINX has no TLS or crypto stack of its own. The package links `libssl.so.3`/`libcrypto.so.3` dynamically (`ldd`), so the handshake, ciphers and certificate checks all belong to the system OpenSSL. NGINX owns policy and plumbing: directives → `SSL_CTX` calls, SNI → `server` selection, ALPN choice, the shared session cache, ticket keys, OCSP fetching, and the QUIC transport (TLS inside QUIC is still OpenSSL, via the compat layer).
  * The handoff runs in layers: Ubuntu compiles in a floor (`-DOPENSSL_TLS_SECURITY_LEVEL=2`). NGINX loads `openssl.cnf` at startup (`system_default`: `CipherString = DEFAULT:@SECLEVEL=2`), then applies its own directives to each `SSL_CTX`, and whatever is set last wins. A plain `ssl_ciphers` without `@SECLEVEL` keeps the inherited level.
  * With `ssl_protocols TLSv1 TLSv1.1 ...` alone: alert 70, logged as `unsupported protocol`. Any one of these unlocks both versions: `ssl_ciphers DEFAULT@SECLEVEL=0`, `ssl_conf_command CipherString DEFAULT@SECLEVEL=0`, or (system side, no NGINX change) an `openssl.cnf` whose `system_default` sets `@SECLEVEL=0`, pointed to with `OPENSSL_CONF`. Editing `/etc/ssl/openssl.cnf` itself would lower the floor for every OpenSSL app on the host.
  * BIG-IP delta: no equivalent of a vendor-owned TLS stack. The crypto library's version and distro patches are part of NGINX's behavior. Other builds can link BoringSSL, AWS-LC, LibreSSL or quictls instead.

* **Q: Patching OpenSSL under a running NGINX.** Walked through on the Day 1 lab (`libssl3` `3.0.2-0ubuntu1.10` → `1.30`):
  * **The version string never changes.** `openssl version` and `nginx -V` both still say `3.0.2 15 Mar 2022` after the upgrade. Ubuntu backports fixes into the release's upstream version, so the package revision (`dpkg -l libssl3`, `apt changelog libssl3`) is the real patch level. `nginx -V` is build-time information anyway. The box had been ~20 security revisions (≈3 years) behind while NGINX itself was current.
  * **After `apt`, the running NGINX keeps the old library:** `/proc/<pid>/maps` shows `libssl.so.3 (deleted)`.
  * **`nginx -s reload` doesn't fix it.** The new workers are copies of the old master and still had the deleted library loaded.
  * **`kill -USR2` fixes it with zero downtime.** The new master re-executes `/usr/sbin/nginx` and loads the patched library, and both generations serve until `WINCH` (old workers drain) and `QUIT` (old master exits). Until `QUIT`, `HUP` to the `.oldbin` master is the rollback. Right after `USR2`, `nginx.pid` briefly doesn't exist yet. The nginx.org package's `/etc/init.d/nginx upgrade` scripts the same sequence, and `systemctl restart` is the version with a gap.
  * **Detection:** `/proc/<pid>/maps` is the ground truth, but grep for `lib(ssl|crypto).*(deleted)`. A bare `(deleted)` also matches NGINX's shared memory zones (`/dev/zero (deleted)`) and each worker's `/[aio] (deleted)`, which are normal. `lsof +L1` misses mapped libraries; use `lsof -nP | grep DEL`. `needrestart` flagged `systemd-logind` and `cloud-final` but **not** the lab NGINX started from a shell, so don't count on it for processes outside systemd.
  * BIG-IP delta: a TLS stack fix there is an F5 hotfix image and a reboot. Here the package manager swaps the library under a running process, and you choose when NGINX picks it up. SBOM view: packaged NGINX inherits the host's `libssl3`, a container image carries its own (rebuild/re-pull), and a `--with-openssl=` build compiles it in (rebuild; package scanners may miss it).

* **Q: Can this box get OpenSSL 3.5 for post-quantum hybrids?** Not from `apt`: Ubuntu 22.04 stays on 3.0.2 (backports only), and 24.04 is on 3.0.13. 26.04 ships `3.5.5`. Replacing the system `libssl3` by hand would break apt-managed software, and a custom `--with-openssl=` NGINX build takes you off the packages. The cheap path is the official `nginx:mainline` image (Debian 13, nginx 1.31.6, `built with OpenSSL 3.5.6 ... (running with OpenSSL 3.5.7)`, another build-vs-runtime example). Verified on 8089 with the lab ECDSA cert and **no NGINX PQ config**: a 3.5 client negotiated `X25519MLKEM768` by default, and the host's 3.0.2 client fell back to `X25519`. The hybrid key shares are 1216 bytes (client) and 1120 bytes (server) versus 32 for X25519, so the ClientHello can exceed one packet. The certificate (authentication) is still classical; only key exchange is PQ.

* **Quiz:** 9/10 on the first attempt. Day 1 recap written: `day01_recap.md`.
* **Recap asset:** `aead-vs-cbc.png` (+ `.svg` source, Lato, rendered with resvg at 2x): MAC-then-encrypt vs AEAD record protection, the CBC/RC4 attack timeline (padding oracle 2002 → Zombie POODLE/GOLDENDOODLE 2019, incl. BIG-IP CVE-2014-8730), what AEAD doesn't fix, and the `ssl_ciphers` vs `Ciphersuites` split.

* **Q: Do `ssl_protocols` and `ssl_ciphers` have to be set together?** No, they're independent filters and a handshake needs a protocol *and* a suite valid for it. `ssl_ciphers ECDHE+AESGCM` alone, with default protocols: TLS 1.0 still gets alert 70 from `ssl_protocols`. Two real couplings: `@SECLEVEL` inside the `ssl_ciphers` string gates protocols (Activity 3.2), and an AEAD-only TLS 1.2 list leaves TLS 1.0/1.1 with no usable suite. Activity 3.3's `ssl_protocols TLSv1.2 TLSv1.3` only restates the 1.31.6 default; it's pinning policy so a config doesn't depend on version defaults (older NGINX enabled TLS 1.0/1.1).
* **`ssl_conf_command` behavior** (8088):
  * A typo is caught by `nginx -t`: `[emerg] SSL_CONF_cmd("Ciphersuites", ...) failed ... no cipher match`.
  * It is applied after the native directives: `ssl_conf_command CipherString ECDHE+AESGCM` beat `ssl_ciphers HIGH:!aNULL` in either file order.
  * **Inheritance trap (like `add_header`):** `Ciphersuites` at `http` plus *any* `ssl_conf_command` in the `server` (e.g. `Options PrioritizeChaCha`) dropped the inherited TLS 1.3 policy and AES-128 was accepted again. Only at `http` = enforced.
  * Keeping policy coherent: one `tls-policy.conf` snippet included at `http`, never `ssl_conf_command` at lower levels; or system-wide via `openssl.cnf` (`Ciphersuites` under `system_default`), which `nginx -T` doesn't show.
* **`grep: logs/error.log: binary file matches`:** a client whose own OpenSSL refuses TLS 1.1 still opens TCP and sends a TLS alert 70 (`15 03 03 00 02 02 46`, captured with `nc`). Sent to the plain-HTTP 8083 server, NGINX logged it as the request line (`client sent invalid method ... request: "\x15\x03..."`, access log `400 sni=-`). GNU grep then treats the whole log as binary. Use `grep -a`.

## Day 2
* **Q: What is Huffman coding?** (From RFC 7541, not a lab test.) It is a prefix code in which frequent symbols get short codes and rare ones get long codes. Because no code is a prefix of another, the decoder needs no separators. HPACK uses one **fixed** table (Appendix B), built from real-world header statistics: `0-2 a c e i o s t` take 5 bits, and rare bytes take up to 30 bits. For each string, the encoder sets an H bit and Huffman-codes the string only when the result is shorter, then pads to a byte boundary with 1s. The table is static on purpose. SPDY's adaptive DEFLATE mixed secrets with attacker-supplied text, and the compressed length leaked the secrets (CRIME). Huffman codes each byte on its own, so the length reveals nothing about neighbouring data. The cross-request risk sits in the dynamic table, which has the "never indexed" literal for that reason.
  * It explains Activity 3.3's `len=422`: 600 × `a` at 5 bits = 375 bytes, and the pseudo-headers, the name and the other headers make up the rest. The drop to `len=11` is the dynamic table, not Huffman.
* **Q: Does QUIC solve the transport-layer head-of-line blocking that HTTP/2 can't?** (From RFC 9000/9204, not a lab test; loopback drops no packets, so the lab can't show it.) Yes. Ordering is per stream, so a lost packet stalls only the streams whose data it carried. Each packet is encrypted on its own, so there are no TLS records spanning lost packets. QPACK replaces HPACK because a dynamic table that assumes in-order arrival would bring the blocking back: table updates go on their own stream, and `SETTINGS_QPACK_BLOCKED_STREAMS` caps how many requests may wait on a missing update. What remains: ordering within one stream, a congestion window shared by the whole connection, packets that carry frames for several streams, and the fallback to TCP/HTTP/2 when UDP is blocked.
* **Box hang in Activity 3.6 (fixed in `helpers.sh`, `test_sprint03.sh` and the guide):** after the catch-all got `listen 8443 quic reuseport default_server`, the first `h3 ... evil.example` command (no `--max-time`) froze the host. SSH and the shell died, journald missed its 3-minute watchdog, and the instance was powered off. NGINX logged nothing unusual. Reproduced on 8088 with a capped container: `alpine/curl-http3:8.11.0` (quiche) retries the refused handshake about 130 times per second (518 `handshake rejected while handling frames` at `info` in 4 s) at 100% CPU, and its memory grows about 130 MB/s. With `--memory 512m` it was OOM-killed in 4 s (exit 137). Without a limit, 7.5 GB and no swap last about a minute. NGINX's workers stayed at <1% CPU and 7 MB RSS: the client is at fault, not the server. Fix: the helpers now run with `--memory 1g --memory-swap 1g` and default to `--max-time 5`, so the refused case prints `000` (curl exit 28) after 5 s at about 470 MB.
* **Q: Where does the HPACK table live, and is it the same on both sides?** There are two tables per direction per connection, and each pair is a mirror. Requests: the client's encoder table and NGINX's decoder table. Responses: NGINX's encoder table and the client's decoder table. Neither side sends a table. Each header block carries instructions ("add this", "use entry 62") that both sides apply, so the copies stay identical. The decoder bounds the size with `SETTINGS_HEADER_TABLE_SIZE` (default 4096 bytes; an entry costs name + value + 32). Old entries are evicted first-in, first-out. In NGINX the tables belong to the HTTP/2 connection inside the worker that owns it: they aren't a shared zone, and they're freed when the connection closes. Verified on 8088 with Python `h2` (3 requests on one connection):
  * NGINX's SETTINGS had no `HEADER_TABLE_SIZE`, so its request decoder table is the default 4096 bytes. The client's encoder had 5 entries indexed, which is why Activity 3.3's repeat costs `len=11`.
  * **NGINX doesn't compress responses with the dynamic table.** The first response header block starts with `0x20`, a dynamic table size update to 0, which turns off its encoder table for the rest of the connection. After that come static-table and literal entries. The response header blocks were 120, 119 and 119 bytes, and the client's decoder table stayed empty. Responses still get the static table and Huffman coding, but repeats never get cheaper.
* **Journal 3.3 (who gains most from HPACK):** the mobile client. Request headers go **up**, and a mobile uplink is the narrow, high-latency side. Dozens of requests per page each repeat a large cookie, so compressing them means more requests fit in TCP's first few round trips. Server-to-server calls run on fast links where bytes matter less. Often they don't use HPACK at all: NGINX's own upstream is HTTP/1.1 by default (§1.3). A fixed bearer token compresses fine, but per-request signatures (AWS SigV4-style, nonces) change every time and don't compress.
* **Journal 3.2 (80 assets):** handshakes = connections, not assets ÷ connections. 80 ÷ 6 ≈ 13 is requests per connection. HTTP/1.1 makes up to 6 handshakes per host (12 for two hosts), and HTTP/2 makes 1 per host. With session resumption, most of the extra HTTP/1.1 handshakes are abbreviated. HTTP/2 **connection coalescing** lets the browser reuse one connection for a second hostname when the certificate covers both names and the name resolves to the same IP. Wildcard or SAN certificates then mean 1 handshake in total. A server that gets a coalesced request for a name it doesn't serve answers 421 Misdirected Request. (Coalescing is from RFC 9113 §9.1.1, not a lab test.)
* **Q: How do HTTPS DNS records advertise HTTP/3, and how does that differ from `Alt-Svc`?** (RFC 9460, record type 65.) `Alt-Svc` comes in a response, so the first visit always uses TCP + TLS + h2, and QUIC is used only on later connections (for `ma` seconds). An HTTPS record is looked up alongside A/AAAA (`1 . alpn="h3,h2" port=8443 ipv4hint=...`), so the **first** connection can use QUIC. The record can also carry address hints, an ECH key (the main reason the record type exists), and AliasMode (priority 0, CNAME-like at the zone apex). Its presence makes clients upgrade `http://` to `https://`, the same way HSTS does. The DNS zone owner controls the record, not NGINX. Client support varies, and Firefox, for one, uses it only with DoH, so keep sending `Alt-Svc` too. Checked live: `www.google.com` → `1 . alpn="h2,h3"`. `cdn.f5.com` (a CNAME to CloudFront) → `1 . alpn="h2"`, with no `Alt-Svc`, and HTTP/3 to it timed out while HTTP/3 to cloudflare.com worked from the same box. Having the record doesn't mean having HTTP/3: a CDN publishes whatever is enabled for that distribution. (The infographic uses cdn.f5.com instead of cloudflare.com, which showed `alpn="h3,h2"`.)

## Day 3
* **Q: Where in the worker can a request/response be changed?** Requests go through fixed **phases**: `POST_READ` (realip) → `SERVER_REWRITE` / `FIND_CONFIG` / `REWRITE` (`rewrite`, `set`, `if`, `return`) → `PREACCESS` (`limit_req/conn`) → `ACCESS` (`allow/deny`, `auth_basic`, `auth_request`) → `PRECONTENT` (`try_files`, `mirror`) → `CONTENT` (`proxy_pass` builds the upstream request; `proxy_set_header` is evaluated here) → `LOG`. Responses don't have phases. Upstream headers are first copied by the proxy module (`proxy_hide_header`, `proxy_pass_header`, `proxy_redirect`, `proxy_cookie_*`), then pass through the **header filter chain** (`add_header`, gzip, range, …) and the **body filter chain** (`sub_filter`, gzip). The last header filter serializes the status line and adds `Server`/`Date`. The directive's module decides its phase, not its position in the file. Verified on 8088:
  * `deny all; return 200 ...;` in one location → 200. `return` runs in REWRITE, before ACCESS.
  * `add_header Server mine;` → **two** `Server` headers (`nginx/1.31.6` and `mine`). `add_header` appends to the list, and the core still writes its own at serialization.
  * Proxied: NGINX hides the upstream `Server` by default and sends its own. `proxy_pass_header Server;` sent the backend's `SimpleHTTP/0.6 Python/3.10.6` and **no** NGINX one, because the core adds `Server` only if none is set. That is an open-source way to avoid the NGINX banner, but only on proxied responses. (Plus `server_tokens ""` and headers-more `more_clear_headers Server` act on that same "already set / empty" slot.)
  * **Where headers-more fits:** it is a **header filter** module, so it runs inside the header filter chain, after the proxy module has copied upstream headers in and before the final header filter writes the response out. `more_clear_headers Server` fills the core's `Server` slot with an entry marked "don't send". The final filter sees the slot is taken and doesn't add its own, then skips the marked entry, so no `Server` goes out. A third-party filter is registered after the core filters, so it runs **before** `add_header`. Verified with headers-more v0.37 built `--with-compat` as a dynamic module against 1.31.6 (official `nginx:mainline` container; Ubuntu's `libnginx-mod-http-headers-more-filter` is built for 1.18 and won't load):
    * `more_clear_headers Server` → no `Server` on a `return 200`, on a `return 404` and on a proxied response.
    * `more_set_headers "Server: lumina"` → `Server: lumina` (replaces it rather than adding a second one).
    * `more_clear_headers Server` + `add_header Server mine` → only `Server: mine`. headers-more ran first, and `add_header`'s entry was appended after it.
* **Activity 3.4 result and new Activity 3.5 (`include` snippets), checked on 8088/8089 against a copy of `day3_nginx.conf`:**
  * `server_tokens off` at `http` also covers the redirect server (`Server: nginx` on the 301).
  * **`proxy_hide_header` has the `add_header` inheritance trap:** with `proxy_hide_header X-Handled-By` at `server`, adding `proxy_hide_header X-Powered-By` in `location /api/` brought `X-Handled-By: api-node-1` back.

## Day 3 Side Quest
* **Q: Is the lab ACME v1 or v2?** It's v2 only. "ACMEv2" is the standardized protocol, RFC 8555. "ACMEv1" was Let's Encrypt's pre-RFC draft protocol, and Let's Encrypt switched it off in 2021. Pebble speaks only RFC 8555, and `nginx-module-acme` 0.4.1 has no v1 code and no setting to choose a version. **How to tell them apart:** look at the directory object. A v2 directory lists `newNonce`, `newAccount`, `newOrder`. A v1 directory listed `new-reg`, `new-authz`, `new-cert`. v2 also signs every request with the account URL (`kid`), and it fetches resources with signed POST-as-GET instead of plain GET. Strings in the module binary show it implements `newNonce`/`newOrder`/`kid`, `renewalInfo` (ARI, RFC 9773), `replaces`, `profiles` and `externalAccountBinding`. It solves only `http-01` and `tls-alpn-01`. `dns-01` appears only as a challenge type it can recognize, with no solver, so it can't do wildcards. The lab's `pebble-config.json` offers a `default` profile (90 days) and a `shortlived` profile (6 days).
* **ACME on BIG-IP itself: [kojot-acme](https://github.com/f5devcentral/kojot-acme)**, built by Kevin Stewart (F5) and published under f5devcentral. It runs an ACMEv2 client on the BIG-IP, using a modified `dehydrated` client started by `f5acmehandler.sh` and scheduled by cron (`--schedule`). It supports **HTTP-01, DNS-01 and TLS-ALPN-01**, as well as External Account Binding:
  * **HTTP-01:** an iRule (`acme_handler_rule`) on the port 80 virtual servers answers the challenge from tokens kept in the `dg_acme_challenge` data group.
  * **TLS-ALPN-01:** answered by an overlay virtual server.
  * **Configuration:** the list of certificates lives in the `dg_acme_config` data group. It can also create and attach the client SSL profile (`CREATEPROFILE`). In HA pairs it syncs through iFiles.
  * Compared with `nginx-module-acme`, both put the ACME client on the proxy itself, but kojot-acme also covers DNS-01, and so wildcards.
* **Q: Does the NGINX Plus API have transactions, like iControl REST's `/mgmt/tm/transaction`?** No. There's no transaction endpoint and no optimistic locking. Each single-key write is atomic, so a handshake sees either the old value or the new one, never a mix. A change that has to cover several keys can't be made atomic. Verified on a scratch R37.1 container (API 10, port 8088):
  * `PATCH` with two keys → `400 only one key can be updated`. A `POST` of several keys works **only on an empty zone** (`201`); on a non-empty zone it fails with `400 only one key can be added`. A `POST` of a key that already exists → `409`.
  * The API sends no `ETag`, and it ignored `If-Match: "nope"` (`204`, value changed). 50 concurrent `PATCH`es to one key all returned `204`, and an arbitrary one won (`w39`). Last writer wins, with no conflict detection.
  * "Delete the zone, then `POST` everything" is not a transaction: between the two calls the store is empty, and handshakes fail.
  * **Patterns instead:** (1) put whatever must change together into **one value** (the key + cert bundle is the transaction); (2) give each writer its own keys (one key per hostname); (3) serialize writers in the automation (one pipeline, or a lock). The transactional unit NGINX does have is the **reload**: the whole config is checked and loaded completely or not at all, and a failed reload leaves the old config running. That is coarse-grained, and it costs new workers. At fleet scale, NGINX One / Instance Manager publish whole configs (Sprint 11), like BIG-IQ.
* **Journal A.5 (where does the state file's private key live, and who can read it?):** first, there are three copies of the private key, not one. They sit in the state file, in shared memory, and behind the API.
  * **Lab, as it is now:** `plus/state/lumina_certs.json` is mode `644`, so anyone can read it, inside a `777` directory. On the host it's owned by `systemd-resolve`, because the container's `nginx` user is UID 101 and the host gives UID 101 to `systemd-resolve`. Any local user, and any host service running as UID 101, can read the key. Compare B.2: there the key file is `666`, and the module's `700` directory is what protects it.
  * **The API is the bigger leak:** a **read-only** `api;` (no `write=on`) still returns the PEM with `GET /http/keyvals/...` (verified on a scratch R37.1 container; `PATCH` → `405`). So does the dashboard's API access. Anyone allowed to look at the dashboard can download the private keys.
  * **Production answer:** prefer **no `state=` at all**. Keep the key in a secrets manager or HSM as the source of truth, and have the controller re-push it after every start. Readiness/health checks must stay red until the store is loaded, because an empty store means alert 80. If you must persist: give it a dedicated directory owned by the worker user, mode `700`, on an encrypted volume. Keep it out of images, git and unencrypted backups, and away from core dumps (shared memory holds the key). Put the API on a Unix socket or loopback, behind mTLS or auth plus `allow`/`deny`. A read-only API for monitoring still sees every zone in `http`, so block the keyvals path in its location (for example `location ~ ^/api/[0-9]+/http/keyvals { deny all; }`), or don't give monitoring the API at all. Push keys over TLS, never over plain HTTP across a network.
  * **Who can read:** the NGINX worker user, root, members of the `docker` group (equivalent to root: `docker cp`/`exec`), backup systems, and anyone who can reach the API. Shrink each of these on purpose.
* **Journal B.3 (which part gives you the certificate, which swaps it live, and could they be combined?):** the trick in the question is that **both** swap it live. Part B (ACME) **obtains** the certificate. Part A (keyval + API) **delivers** a certificate that came from somewhere else. Neither one needs a reload, because in both `ssl_certificate` is a **variable** that is evaluated per handshake from shared memory. Verified on scratch ports (8088/8089, Pebble on 14100, set to issue 3-minute certificates):
  * Issued 18:17:25, "renewal scheduled at 18:18:53". The new certificate arrived at 18:19:54, about a minute after the scheduled time. Across the swap: 0 failed handshakes in ~800 tries, the same worker PIDs, no reload in the log, and the next renewal was scheduled right away.
  * There were only 3 `acme-challenge` requests in total, all from the first order. The renewal reused the authorization that was still valid, so it didn't validate again.
  * Side note: Part B's real run issued a **6-day** certificate (Oct 19 → Oct 25), which matches the guide.
  * **What sets them apart:** ACME only covers names that a public-style CA can validate over HTTP-01/TLS-ALPN-01. Keyval takes any certificate: an enterprise PKI, an HSM-backed CA, EV/OV certificates, wildcards obtained elsewhere through DNS-01. It hands you an API, and the private key then becomes something you have to protect (A.5).
  * **Combining them:** not inside NGINX. The module documents no way to feed its certificates into a keyval zone, and `$acme_certificate` is a separate variable. Each `server` uses one or the other: ACME for public names, keyval for the rest, side by side in one instance. Or combine them outside NGINX: an external ACME client (DNS-01 for wildcards) or an enterprise CA, with automation pushing the result through the keyval API. That is the BIG-IP kojot-acme pattern of an ACME client plus a push into the running proxy, applied to NGINX Plus.
